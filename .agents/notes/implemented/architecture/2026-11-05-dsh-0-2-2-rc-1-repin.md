# Agent Note: The wire contract moved to dsh 0.2.2-rc.1

Status: implemented

## Problem

The client still declared `dsh-v0.2.0-rc.2` while the host line it is deployed
against had moved on: the running fork release is
[`dsh-v0.2.1-rc.3-chance.2`](../../../../reference/README.md) and the next one,
`dsh-v0.2.2-rc.1-chance.0`, is built on the official `dsh-v0.2.2-rc.1` tag. The
0.2.2 tree deletes four registered methods this client calls
(`terminal/write`, `terminal/resize`, `schedule/update`, `schedule/delete`) and
the `terminal/follow` stream, replaces the terminal with one duplex
`terminal/attach` stream, moves schedule tasks from Session reminders to a
host-wide store, changes the `session/control` projection increment and the
`session/attachment` request, makes `session/follow` passive unless asked to
activate, and excludes five projections from Session list summaries. The
pinned contract therefore described a superseded host, and several surfaces
were already failing against the deployed 0.2.1 line (the terminal attachment
protocol and the bare-array results of `schedule/catalog` and
`terminal/{shells,list}`).

## Decision

Re-pin to the official `dsh-v0.2.2-rc.1` (`66491b05e3f0`) and migrate the
adapter, domain, and app in one change.

- The pinned surface grows from 128 to **184 unary methods** and from 13 to
  **21 streams**; `declared 105, identical 103, missing 81, client-only 2`.
  The digest covers 41 registration sources.
- The terminal is one duplex stream. Input commands travel up the same mux
  stream (`write`/`resize`, consecutive sequence per attachment) and every
  accepted command is acknowledged; `snapshot`/`state` carry `writable`, so a
  second attachment learns it is read-only from its own frames instead of a
  `controllerId` field.
- Schedule is host-wide: `schedule/edit` replaces update/delete under an
  `expectedUpdatedAt` compare-and-update, `schedule/list` answers a page,
  `catalog` answers a bare array, and create/view/run/deleteInactive/
  deliveryLimits are wired. The settings page keeps its no-create posture; the
  chat reminder strip keeps folding historical version-1 `schedule/change`
  events, which no longer describe new tasks.
- The 0.2.2 shapes that coexist with the deployed 0.2.1 host during the
  rollout are read in both forms: the `changes[]` projection increment and the
  single `key`/`value` one, the reference-shaped and bare-id attachment
  requests, the optional `activate` flag, and the workspace `replace`
  increment. The deprecated shapes are removed when the deployment line and the
  pin agree again.
- Unwired methods are accounted for by namespace in
  [docs/spec.md §4.6](../../../../docs/spec.md#46-wire-coverage); the
  experimental panels the shipped web-app bundle does not mount are recorded
  there rather than added to `out-of-scope`.

## Alternatives considered

Stay on `dsh-v0.2.0-rc.2`: rejected — the client is already wrong for the host
it runs against, and the gate would keep certifying a withdrawn contract. Pin
the fork tag `dsh-v0.2.2-rc.1-chance.0`: rejected — its five extra methods are
additive, and its `subagents` registrations use the decorator object form the
gate cannot parse, so the pin stays the reproducible official tag. Wait for a
0.2.2 stable tag: rejected — the host upgrade is already being published, and a
client that waits ships the breakage. Adapt the client to both contract lines
permanently: rejected — the compatibility branches are transitional and named
as such; one pinned contract remains the rule.

## Consequences

The gate is CLEAN at the new identity. The terminal screen, schedule page, and
image reads work against 0.2.2 hosts and, through the transitional readers,
against the deployed 0.2.1 line. The reminder strip shows no task created after
the host moved to the store; the settings catalog does. A host that still serves
0.2.0 keeps working only where the old shape was a superset (the compatibility
branches), which is why the deployment and the pin move together. The adapter's
fake host now mirrors the real transport for array results: `schedule/catalog`
and `terminal/{shells,list}` had been tested against a wrapper object the host
never sends.
